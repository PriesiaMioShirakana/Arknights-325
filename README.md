# Stronghold C++ 后端

这是正在逐步迁移的后端：可独立构建的 C++23 核心库、原数据的编译期适配器和离线验证程序。原 JavaScript 项目位于相邻的 `Stronghold-Protocol/`，当前对照提交为 `9f6b6d5441934c01fcc4e9e7f7f0130281e0239b`。

**目前可运行基础规则战斗，尚不能替代包含全部技能、羁绊和地图机制的完整游戏后端。** 原项目仍是尚未迁移规则的实现与行为依据。

商店展示不预占库存；购买和奖励领取时扣除。手牌从右向左填充，满手拒绝购买，即便该次购买会触发合成。合成保留实际持有的卡池份数，出售时准确归还，支持原数据中两份合成的例外。升级立即增加商品位，并保留已有商品；冻结未售商品跨回合保留，之后解除冻结。

布阵沿用原 JS 的规则：远程棋子可以部署在地面或高台，普通近战只能部署在地面；特性允许上高台的近战按原数据放宽。场上交换检查双方落点，替换已部署干员不增加部署数量。撤回时可与手牌干员交换；落到道具格时寻找最右侧空位，无空位则拒绝。合成按临时区、手牌、棋盘阅读顺序消耗副本，结果优先落在已消耗棋子中列最靠左、同列内行号最大的合法格，并继承该棋子的朝向。

`EconomySession` 实现基础经济、普通干员／召唤物布阵及库存流转。普通装备支持穿戴、指定替换、锁定销毁、合成与回收；临时栏按首次可操作的准备阶段到期，准备后或战斗中获得的物品留到下一次准备。`GrantPiece` 和 `ApplyInventoryEffect` 是可信内容入口，支持结算赠送、就地晋升／装备升级、变形以及强制移除，不应直接作为客户端命令。消耗型装备与法术通过 `PreparationContent::Execute` 执行；出售、获得干员与战后装备钩子已接入，准备阶段盟约里程碑、永久折扣和刷新奖励已接入，专属战斗内容仍待移植。`LocalMatch` 已组合 DIY／补位、召唤物目录及阶段驱动。`SetBoardLayout` 支持逐玩家替换部署布局，并按阅读顺序回收非法部署；手牌和临时区均满时原地保留。宿主仍需根据实际回合、首领配对及地形效果生成并提交布局；准备阶段召唤物按拥有者、射程和容器堆叠回收，不占干员部署数。这里的 `CLOSED` 只表示经济准备阶段结束，不表示已完成战斗。`RoundLedger::CommitToPreparation` 已接通结算资金和最终淘汰：资金在下轮收入时发放，淘汰归还实际持有份数，重复结算被拒绝；本地宿主按阶段提交这些结果。通用 Scheduler 供调用层使用；Battle 内部的类型化定时队列负责工事破坏、召唤物到期及寒风，保留原回调的同刻顺序与下一帧执行边界。

战斗核心使用已解析的属性、攻击配置和路线输入，独立于经济目录与网络运行。复用索敌和投射物缓冲区，缓存攻击范围和路径后缀距离；以稳定数字 ID 关联单位。内置规则直接调用，仅显式 CUSTOM 标签创建扩展实例并进入 CRTP／派生接口。已经导入双方基础数据、模组／技能选择、补位／自选及地图数据；干员／召唤物配置已导入，具体内容脚本仍在移植，本地宿主已连接准备阶段、基础战斗与下一回合，仍缺少完整内容脚本和机器人策略。详见 [战斗核心接口与范围](docs/battle.md)。

## 构建

需要支持 C++23（包括 `std::expected`）的编译器、CMake 3.25+。带原数据的默认构建还需要 Python 3.10+；Node.js 仅用于可选的 JavaScript 差分测试。程序运行时不需要 Python 或 Node，不下载第三方库。

在 Visual Studio 中打开 `backend` 文件夹，选择 `CMakePresets.json` 的 `default` 配置。命令行可在 Developer PowerShell 中运行：

```powershell
cmake -S D:/Dev/Cpp/Arknights/backend -B D:/Dev/Cpp/Arknights/backend/build/local -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build D:/Dev/Cpp/Arknights/backend/build/local
ctest --test-dir D:/Dev/Cpp/Arknights/backend/build/local --output-on-failure
```

上面的工作区路径仅是本机调用示例。工程文件中的路径均基于 CMake 的项目目录变量，没有写死 Visual Studio 或工作区位置。其他系统可替换 `-S`／`-B` 路径，使用本机 GCC／Clang 工具链。

本机 MSVC 首次 Debug 探测出现 C1902（程序数据库管理器不匹配）。本轮通过在配置命令中追加 `-DCMAKE_MSVC_DEBUG_INFORMATION_FORMAT=Embedded`，使用 `/Z7` 内嵌调试信息完成验证；这一机器相关选项没有强制写入工程默认配置。

本机中文 MSVC 的 `/showIncludes` 输出还受终端代码页影响：初次探测生成了乱码前缀，Ninja 未记录头文件依赖。在 Developer PowerShell 中先执行 `chcp.com 65001`，再用新的构建目录配置，可以正确记录依赖；已通过修改头文件时间戳验证增量编译会重新编译依赖源文件。已有错误缓存的目录需要重新配置（例如 `cmake --fresh`），仅重新运行 build 不会修正探测结果。

构建纯核心及其单元测试、完全不读取 JS 仓库：

```powershell
cmake -S backend -B backend/build/core -DSTRONGHOLD_BUILD_CATALOG=OFF
cmake --build backend/build/core --config Debug
ctest --test-dir backend/build/core -C Debug --output-on-failure
```

通过 `STRONGHOLD_REFERENCE_DIR` 可以指定另一个原项目目录。生成器读取 `config.json`、`chess.json`、`items.json` 和 `stages.json`，生成经济、部署类别和静态地形的 C++ 数据，并记录四个源文件的 SHA-256 指纹。战斗生成器另外读取 `enemies.json`、`stages.json` 和 `waves.json`，生成 `constexpr` 敌人表、黑板、地图、装置、波次与分支表，并记录独立指纹。它不是任意 JSON 导入器，不包含游戏素材；生成文件位于构建目录，不手工维护。干员生成器读取 `chess.json`、`tokens.json`、`backups.json`，枚举有效选择并去重共享范围／黑板表，另存指纹。大型常量表分成 12 个翻译单元，Ninja 数据编译并发限制为 2；所有表仍为静态常量，避免 MSVC 编译单个巨大文件的内存峰值。技能黑板是内容参数，不等于已实现技能脚本。

## 使用与扩展边界

`Stronghold::Core` 是无网络、无 OS API 的库目标；`stronghold_catalog` 提供编译期数据适配，`stronghold_cli` 提供诊断入口：

```powershell
./backend/build/local/stronghold_cli.exe catalog
./backend/build/local/stronghold_cli.exe probe 42
./backend/build/local/stronghold_cli.exe trace 42 mode_multi_normal
./backend/build/local/stronghold_cli.exe boards
./backend/build/local/stronghold_cli.exe placement 42 mode_multi_normal act2autochess_m01 0
```

- 调用方构造 `Catalog` 和 `EconomySession`，显式调用 `BeginRound`、`Execute`、`EndPreparation`。完整阶段流可用 `BeginRound(round, false)` 只发放收入/刷新商店，在机变结束后调用 `BeginPreparation` 处理延迟合成；倒计时结束先调用 `ApplyPreparationDeadline`，执行内容结束效果后再 `EndPreparation`。修改命令返回 `std::expected<ChangeSet, CommandError>`，没有隐式网络发送或事件回调。
- 接入道具时，为 `PreparationContent` 传入 `ReferencePreparationItems()` 和 `PreparationArtRules`，通过它的 `Execute(command, random)` 提交准备命令；每轮使用 `BeginRound(round, false)`，随后调用一次 `OnRoundStart(random)`，完成机变后再 `BeginPreparation`。回合效果按存活玩家、淘汰玩家的顺序执行，重复调用被拒绝。
- `ReferenceStages()` 以常量引用提供静态布局，`StageBoards::At` 选择普通场地或首领左右半场。把布局值传给会话构造函数，核心即可独立于地图文件工作；省略布局会使用原 JS 的降级测试场地（第 9 列不可部署），实际宿主应显式传入地图。
- `ReferenceCatalog` 返回目录值对象；调用方持有 `const Catalog`，会话直接引用目录及其中的模式规则，不使用共享指针。目录必须先于会话构造、晚于会话销毁，使用期间不得移动或重新赋值。构造函数禁止直接绑定临时目录，编译期测试覆盖这个限制。
- 随机流、种子派生、战斗数值阶段及简单目录／卡池操作在头文件中直接定义，可内联；随机流还可在常量表达式中求值。复杂调度与经济事务保留独立实现，没有继承层次或虚函数。
- 会话由一个所有者串行调用。失败命令不改变库存、资金、UID 或随机流；原版满手召唤物撤回失败仍会改变棋盘键的遍历顺序，C++ 保留这一影响后续堆叠 UID 的行为。其余变更通过值事务提交，后续有性能证据时再优化拷贝。
- `CommandEnvelope` 携带玩家 ID 与回合号；回合号用于拒绝旧回合命令。它不提供身份认证、重复请求去重或跨进程持久化，这些由将来的服务适配器补充。
- `View` 返回指定玩家的私有状态副本，`PublicView` 返回玩家 ID、商店等级、准备状态和可见棋盘，不返回资金、手牌、商店或奖励队列。外部接口必须先认证并限制可查询的玩家，不能直接暴露任意 ID 查询。
- `Scheduler` 接收逻辑时间与预算。未来本机宿主、HTTP 服务和集群中的会话所有者可在此边界驱动核心，无需让业务规则依赖工作线程或系统时钟。
- `Battle` 持有输入数据，禁止复制并允许移动，通过 `Step` / `Advance` 显式推进；`Units` / `Players` 提供只读视图，`DrainEvents` 输出事件，`Result` 输出结算副本。`DealDamage` / `Heal` / `AddShield` / `ApplyStatus` / `RemoveStatus` 保留类型化效果入口，后续技能和宿主在此基础上扩展。
- 库使用标准 C++；仅 CMake 按编译器选择告警与浮点选项。当前没有需要 OS 兼容宏的业务实现。命名遵循工作区根目录的 `AGENTS.md`，格式以本机最新 ReSharper 设置为准，见 [格式说明](docs/formatting.md)。
- 本机 ReSharper 的当前持久化设置与安装版本默认值记录在 `docs/resharper-formatting.json`；没有恢复自动生效的 `.clang-format`。

## 验证

历史基线在 Windows x64 验证过 MSVC 19.51（C++23/latest）和 GCC 13.1。最近完整回归使用 Linux x64、GCC 14.2.1：106/106 项通过（`build/gcc14-debug/operator-kits-tinman-tests.log`）。新增功能尚未重新验证 MSVC、Clang 或 macOS。原五项基线测试及后续范围如下：

1. 核心测试八组：随机流、计时器、卡池、战斗数值、经济、布阵边界，以及 3,000 次混合经济／布阵命令下的卡池守恒。布阵测试包含非法高台交换、满员替换、满手撤回失败、转向和已部署副本合成后的落点与朝向。
2. 实际数据目录加载检查：381 条定义、9 个模式。
3. JS 差分测试：6 个种子的随机／抽卡／伤害探针、3,744 个经济快照、10,584 个包含布阵的快照，以及全部 13 张地图的 39 个场地布局与商店干员／精锐的部署类别。快照比较资金、商店、UID、手牌、冻结、奖励、场上位置及朝向。

4. 战斗核心测试八组：输入校验与时钟、阻挡和行动顺序、伤害／护盾／治疗、路线与超时、DP 再部署和投射物、多人部署顺序及归属。包含旧生命周期的投射物不能击中再部署单位、状态刷新／到期／驱散、免疫、阻挡释放、冷却暂停与前摇重启。
5. 战斗 JS 差分测试：9 个种子的基础／状态场景、6,480 帧，逐帧比较位置、HP、隐藏、阻挡、攻击冷却、部署序号、伤害／治疗／击杀、DP 和结算；同时逐条比较攻击时刻与目标，并比较四种状态剩余时间。断言实际出现治疗、阻挡、消失、再部署、击杀和四种状态，避免空场景通过。
